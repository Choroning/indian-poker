## 1. 박철원님은 누구인가

기존 메모리(`~/.claude/projects/.../memory/`)에 이미 저장된 내용과 중복되지 않는 선에서, 이 프로젝트와 직접 관련된 사실만 요약:

- **소속:** 고려대학교 세종 CSE, 2026년 기준 3학년 (편입 준비 중).
- **직전 학기 경험:**
  - 2025 봄학기 **컴퓨터네트워크** — 텀 프로젝트로 Python 기반 Simple HTTP Server 를 이미 작성해봄. HTTP 메시지 파싱 경험 있음.
  - 2025 봄학기 **객체지향프로그래밍** — 텀 프로젝트로 Java `ServerSocket` 기반 멀티플레이어 챗봇 서버/클라이언트를 작성. **Thread-per-connection** 모델은 이미 경험.
- **현 학기 경험:**
  - 2026 봄학기 **운영체제** — `select(2)` 를 막 배운 시점. 이 프로젝트를 고른 동기의 절반이 "배운 `select` 를 실제로 써보고 싶다" 임.
- **언어별 숙련도 (대략):**
  - C++: 중급 (`24Fall_CPP-Practice` 레포 참고). RAII 는 이해하지만 BSD 소켓 API 는 처음.
  - Java: 중상급.
  - Python: 중상급.
  - JavaScript/DOM: 기본. React 같은 프레임워크 경험은 낮을 수 있음.
- **학습 스타일:** 개념을 빨리 잡는 편이고, 말이 많으면 지루해함. 설명은 짧게, 코드/다이어그램으로 보여주는 게 잘 먹힘.
- **커뮤니케이션 언어:** 한국어.

## 2. 이 프로젝트의 **진짜** 목적

"작동하는 인디언포커 게임" 은 부산물이고, 실제 목적은 다음과 같다 (브레인스토밍에서 박철원님이 직접 정리):

1. raw TCP 위에 **실제 애플리케이션 프로토콜을 설계/파싱** 하는 경험.
2. **WebSocket 프로토콜(RFC 6455) 을 직접 구현** — 핸드셰이크, 프레임, 마스킹, 프래그멘테이션, 컨트롤 프레임까지.
3. **`select(2)` 기반 단일 스레드 이벤트 루프** 를 직접 돌려보는 경험.
4. **네트워크와 게임 로직의 엄격한 분리** — OOP 에서 배운 추상화/캡슐화의 실전화.
5. 마지막으로, 친구와 **실제로 돌려볼 수 있는 결과물**.

→ 이 우선순위를 **코칭 세션 내내 머릿속에 두고** 판단하세요. "지금 이 고민은 학습 목표에 기여하는가?" 는 탈선을 막는 좋은 질문.

## 3. 절대 원칙 (이건 어겨선 안 됨)

### 3.1 학습을 빼앗지 마라
**정답 코드를 먼저 보여주지 마라.** 박철원님이 명시적으로 "그냥 솔루션 코드 보여줘" 라고 요청하지 않는 한, 다음 힌트 사다리를 엄격히 타고 내려가세요:

1. **개념 질문으로 되돌리기** — "지금 이 단계에서 서버가 해야 할 일이 한 줄로 뭐야?"
2. **관련 문서/RFC 섹션 가리키기** — "RFC 6455 §5.3 첫 단락 다시 읽어봐."
3. **테스트 코드만 보여주기** — 계획서의 해당 Task 테스트 블록을 보여주고 "이걸 통과시키는 함수를 네가 써봐."
4. **인터페이스/시그니처만 보여주기** — 헤더에 선언만 주고 구현은 본인이.
5. **가장 막힌 한 부분만 보여주기** — 예: 마스킹 XOR 루프 3줄.
6. **전체 레퍼런스 보여주기** — **최후의 수단.** 30 분 이상 진전이 없고 박철원님이 명시적으로 요청할 때만.

### 3.2 테스트 우선
계획서의 모든 non-trivial Task 는 "실패하는 테스트 → 구현" 순서. 박철원님에게도 이 흐름을 강제하세요. 먼저 테스트를 쓰고, 실패 확인하고, 그 다음에 구현. 이 규율이 프로젝트 전체의 척추.

### 3.3 박철원님이 속도를 낼 때는 **끼어들지 마라**
박철원님이 막힘 없이 잘 가고 있으면 묵묵히 응원. 코칭은 요청이 있을 때 또는 **명백히** 막혔을 때만.

### 3.4 스타일 꼬투리 금지
이름, 들여쓰기, 줄바꿈 같은 표면적인 것은 건들지 마세요. 문제를 지적할 때는 반드시 **기능적/구조적 근거** 가 있어야 함. 박철원님 사기 꺾기 금지.

### 3.5 "네 코드가 틀렸고 레퍼런스가 정답" 은 금지
여러 정답이 있습니다. 레퍼런스와 다르지만 올바른 구조면 "이것도 좋아, 오히려 이 점에서 더 나아" 로 말하세요. 차이가 실질적 문제를 일으킬 때만 지적.

### 3.6 커밋/푸시는 명시적 요청이 있을 때만
메모리에 이미 있는 규칙. 코칭 중 커밋할 때는 박철원님에게 "지금 커밋할까?" 먼저 물어보기. 커밋 메시지는 영문, 간결, 의도 중심. 이 레포는 2026+ 이므로 `Co-Authored-By: Claude Opus 4.6 (1M context) <noreply@anthropic.com>` 트레일러 필수.

## 5. 마일스톤별 단골 함정과 힌트

각 마일스톤에서 박철원님이 자주 막힐 만한 지점들과, 그때 꺼낼 힌트. **박철원님이 그 지점에 도달하기 전에 선제적으로 꺼내지는 말기** — 학습을 빼앗는 짓.

### Phase 1 (M1) — TCP 에코 서버 with `select(2)`

- **함정:** non-blocking `accept()` 가 `-1` 을 돌려주는 게 에러가 아니라 "지금은 새 연결 없음" 일 수 있다.
  - 힌트: "`man 2 accept` 의 `EAGAIN` / `EWOULDBLOCK` 항목 읽어봐. non-blocking 소켓의 관례야."
- **함정:** `select()` 첫 번째 인자 `nfds` 가 "fd 개수" 가 아니라 "가장 큰 fd 값 + 1" 임.
  - 힌트: "`man 2 select` 의 `nfds` 설명 다시 보기. `plus one` 이라는 단어 찾을 때까지."
- **함정:** 매 루프마다 `fd_set` 을 `FD_ZERO` 로 다시 세팅 안 함. `select()` 는 인자를 제자리에서(in-place) 수정함.
  - 힌트: "`select()` 가 네 `fd_set` 을 어떻게 바꾸는지 manpage 에서 확인해봐. 매번 새로 채워야 할 수도 있어."
- **함정:** `SO_REUSEADDR` 을 안 켜서 재시작 후 `bind` 가 `Address already in use` 로 실패.
  - 힌트: 박철원님이 정확히 이 에러를 보면 즉시 "`SO_REUSEADDR`" 키워드 하나만 던져주기.

### Phase 2 (M2) — HTTP Upgrade 핸드셰이크

- **함정:** `Sec-WebSocket-Accept` 계산 순서를 헷갈림.
  - 힌트: "RFC 6455 §1.3 에서 계산 공식 그대로 따라가봐: `key + magic-GUID` 이어붙이기 → SHA-1 → 20바이트 raw 결과 → base64. 중간에 hex 로 바꾸는 단계 **없음**."
- **함정:** `Connection: keep-alive, Upgrade` 처럼 값이 콤마 리스트로 올 때 단순 `==` 비교가 실패.
  - 힌트: "브라우저에서 실제로 어떤 `Connection` 값이 오는지 한 번 찍어봐. `==` 로 비교하면 될까, 아니면 부분 문자열 검색이 나을까?"
- **함정:** 헤더 이름 대소문자 구분해서 비교. HTTP 헤더 이름은 case-insensitive.
  - 힌트: "`Upgrade:` 와 `upgrade:` 가 같은 헤더야. 파서가 둘 다 처리해?"
- **함정:** 헤더 값의 앞뒤 공백 trim 안 함.
  - 힌트: "헤더 값 끝에 `\r` 나 공백이 붙어 있는지 디버그 프린트로 확인해봐."

### Phase 3 (M3) — WebSocket 텍스트 프레임

- **함정:** 방향별 마스킹 규칙 혼동.
  - 힌트: "RFC 6455 §5.3. 클라이언트→서버는 **반드시** 마스킹돼야 하고, 서버→클라이언트는 **반드시** 마스킹되지 않아야 해. 방향마다 다르다."
- **함정:** 마스킹 풀기 XOR 인덱스. 4 바이트 넘어가면 key 가 순환해야 함.
  - 힌트: "`payload[i] ^ key[i % 4]` 여야 해. `i % 4` 빼먹으면 4 바이트 이후부터 엉망."
- **함정:** 확장 길이 (126 → 2 바이트, 127 → 8 바이트) 가 **network byte order (big-endian)**.
  - 힌트: "`ntohs` / `be64toh` 같은 함수 있고, 아니면 직접 시프트로 조립해. 바이트 순서를 확인해봐."
- **함정:** opcode 7 비트로 읽지 않고 상위 비트까지 포함해서 읽음.
  - 힌트: "첫 바이트의 하위 4 비트가 opcode. `b0 & 0x0F` 이지 `b0 & 0xFF` 가 아님."
- **결정적 디버깅 팁:** devtools → Network → WS → Frames 탭에서 박철원님이 보낸 / 받은 바이트를 직접 보여주기.

### Phase 4 (M4) — 프래그멘테이션 + 컨트롤 프레임

- **개념 재강조:** 데이터 메시지가 프래그먼트로 올 수 있음. 첫 프레임은 Text/Binary + FIN=0, 중간 프레임은 Continuation(0x0) + FIN=0, 마지막 프레임은 Continuation + FIN=1.
- **함정:** 컨트롤 프레임(ping/pong/close) 은 프래그먼트 **금지** + 페이로드 125 바이트 **이하**.
  - 힌트: "RFC 6455 §5.4 둘째 단락과 §5.5. 컨트롤 프레임의 두 가지 하드 제약이 있어."
- **함정:** 데이터 프래그먼트 도중에 컨트롤 프레임이 **끼어들 수 있음**. 컨트롤 프레임은 즉시 처리하고, 진행 중인 데이터 버퍼는 건드리지 않음.
  - 힌트: "프래그먼트 중간에 ping 이 오면 어떻게 처리해야 할까? 데이터 버퍼를 비워야 해, 건들지 말아야 해?"
- **함정:** 프래그먼트 시작 프레임의 opcode 를 기억 안 하고 마지막 Continuation 에서 텍스트로 가정.
  - 힌트: "첫 프레임의 opcode 를 어딘가 저장해뒀다가 FIN=1 올 때 재사용해야 해."

### Phase 5~6 (M5, M6) — 세션 레이어 + 로비

- **개념 재강조:** 세션 레이어는 WebSocket 이 아니라 "이미 조립된 JSON 메시지" 를 받음. Layer 1 과 2 의 경계를 엄격히.
- **함정:** 같은 닉네임이 한 방에서 유일한지 체크를 순서를 바꾸거나 빼먹음.
  - 힌트: "PROJECT.md §6.4 의 플로우차트 한 번 더 읽어봐. 순서가 중요해."
- **함정:** 방 코드 혼동 문자 알파벳을 잘못 만들어서 `I`, `O`, `0`, `1` 이 섞임.
  - 힌트: "alphabet 문자열을 눈으로 확인해. 특히 `I` 와 `1`, `O` 와 `0` 을 구분해봐."

### Phase 7 (M7) — 연결 끊김 + 재접속

- **핵심 개념:** "TCP 연결" 과 "세션" 은 다른 수명을 가진다. 박철원님이 이걸 체감하는 게 이 마일스톤의 핵심 학습 포인트.
- **함정:** 재접속 시 기존 Player 객체를 새로 만들어버림 (칩 수가 리셋됨).
  - 힌트: "재접속은 새 Player 를 만드는 게 아니라 **기존 Player 에 새 fd 를 바인딩** 하는 거야. `mark_disconnected` 와 `bind_fd` 의 역할 차이를 봐."
- **함정:** `grace_` 맵의 키를 fd 로 쓰면 새 fd 가 들어올 때 매칭 실패.
  - 힌트: "재접속 매칭의 식별자가 뭐라고 PROJECT.md 에 적혀 있지?"
- **함정:** 게임 진행 중(LOCKED) 에 grace 만료되면 단순 제거만 하고 게임 로직에 반영 안 함. (계획서의 알려진 간극 — "Known Gaps" §12 참조)
  - 힌트: "타임아웃 플레이어는 현재 핸드에서 어떻게 되어야 할까? `IGame::on_player_gone` 이 뭘 해야 할까?"

### Phase 8 (M8) — IndianPoker 게임 로직

- **리트머스 시험:** 게임 로직 파일에서 `send()` / `fd` / WebSocket 타입을 import 하고 있으면 경고. "이 파일은 네트워크를 모른다" 는 원칙 환기.
- **함정:** 베팅 라운드 종료 조건이 두 가지라는 걸 잊음.
  - (a) 모든 active 플레이어가 `current_bet` 에 맞춤
  - (b) 폴드 안 한 플레이어가 한 명만 남음
  - 힌트: "네 명 중 세 명이 폴드하면 어떻게 되지? 카드 공개가 의미 있나?"
- **함정:** `raise` 가 일어나면 "모두 맞췄음" 상태가 리셋되는 걸 놓침.
  - 힌트: "alice check, bob raise 10→20, carol 이 아직 10만 냈어. carol 은 check 해도 돼?"
- **함정:** 시작 플레이어 회전에서 eliminated 자리를 스킵 안 함.
  - 힌트: "다음 핸드의 시작 플레이어를 결정할 때, 죽은 자리는 어떻게 건너뛰지?"
- **함정:** 카드 가시성 규칙이 viewer 기준이라는 걸 놓치고 전역으로 가림.
  - 힌트: "`snapshot_for(nickname)` 이 왜 nickname 인자를 받을까? 카드를 누구 기준으로 숨겨야 하지?"

### Phase 9~10 (M9, M10) — 게임 ↔ 세션 연결

- **개념 재강조:** `Router::fanout_game_state` 의 `__game_state_fanout` 마커 트릭. 게임 로직이 "누구에게 보낼지" 를 모르고 "모두에게 각자 스냅샷" 이라는 지시만 내보내고, 실제 플레이어별 스냅샷은 세션 레이어가 만든다.
- **함정:** `Private` outgoing 을 nickname 이 아니라 fd 로 라우팅하려 함.
  - 힌트: "게임 로직은 fd 를 모르잖아. Private 레코드의 target 이 뭐였지?"

### Phase 11 (M11) — 클라이언트 UI

- **리트머스 시험:** 클라이언트 JS 안에 게임 로직이 섞이면 경고. "내 턴인지" 같은 건 서버의 `current_turn` 필드를 읽으면 됨, 계산하지 말 것.
- **함정:** `sessionStorage` 가 탭별 격리라는 걸 잊음 (→ 새 탭 열어서 저장 내용 공유 안 되는 걸 버그로 착각).
  - 힌트: "`sessionStorage` 가 언제 비어지고 언제 유지되는지 MDN 확인. `localStorage` 와 차이."
- **함정:** `game_state` 메시지 도착 시 전체 DOM 재렌더링 대신 부분 업데이트 시도하다가 상태 꼬임.
  - 힌트: "지금 너의 상태 관리 전략이 뭐야? 서버가 매번 전체 상태를 주는데, 네가 굳이 diff 계산을 해야 할 이유가 있어?"

### Phase 12 (M12) — 보안 마무리

- **함정:** Origin 검증 로직을 핸드셰이크 파서 **내부** 에 넣어서 파서의 순수성을 깨뜨림.
  - 힌트: "파싱과 정책 판단은 다른 관심사야. Origin 을 'allowed' 인지 판단하는 코드가 파서 안에 있으면 테스트가 지저분해지지 않을까?"

### Phase 13 (M13) — 배포

- **함정:** Vercel 이 HTTPS 이므로 `ws://` 로 접속하려 함 → mixed content 차단.
  - 힌트: "브라우저 콘솔에 뭐라고 뜨는지 봐. `wss://` 여야 하는 이유가 있어."
- **함정:** `cloudflared ingress` 에 `noTLSVerify: true` 를 빼먹음 → 로컬 HTTP 업스트림을 Cloudflare 가 거부.
  - 힌트: "`cloudflared` 가 업스트림의 TLS 인증서를 검증하려고 하는 거야. 업스트림이 HTTP 일 때는 뭘 꺼줘야 하지?"

## 6. 가이드 학습 세션을 시작할 때의 절차

박철원님이 "인디언포커 가이드 학습 시작하자" 같은 요청을 하면:

### 6.1 먼저 확인
1. `git fetch` 로 레포 상태 싱크.
2. 현재 브랜치/워크트리 상태 확인.
3. 박철원님이 이미 `guided-learning` 같은 브랜치를 만들어 둔 상태인지, 아니면 이번 세션에서 새로 시작하는지 파악.

### 6.2 새로 시작하는 경우
`main` 에 있는 레퍼런스 솔루션은 건드리지 말고, **계획 커밋(이 플레이북이 추가된 직전의 커밋)** 을 기준점으로 `guided-learning` 브랜치 만들기:

```bash
# 계획 문서 커밋 해시 찾기
git log --oneline | grep "M1-M13 TDD implementation plan"
# 나온 해시를 SHA 로 사용
git checkout -b guided-learning <SHA>
```

이 상태는 "설계 문서 + 구현 계획 + 이 플레이북" 만 있고 M1 이후 코드는 없는 상태. 박철원님이 여기서부터 손으로 써내려감.

### 6.3 이어서 하는 경우
박철원님이 지난 세션에서 어디까지 했는지 이 문서의 §8 Session Log 를 읽고 파악. 마지막 커밋의 메시지도 단서.

### 6.4 오늘 할 마일스톤 확인
한 세션에 한두 마일스톤이 현실적. "오늘 M1 천천히 갈까, M1+M2 같이 갈까?" 정도로 물어보기. 욕심 내지 않기.

### 6.5 Task 단위 진행 루프
각 Task 는 계획서([`../docs/plans/2026-04-11-implementation-plan.md`](../docs/plans/2026-04-11-implementation-plan.md)) 의 해당 섹션을 그대로 사용:

1. **목적 요약** — 박철원님에게 한 문장으로 "이 Task 가 뭘 만들려는 건지" 물어보기.
2. **테스트 먼저** — 계획서의 테스트 코드는 박철원님에게 보여줘도 **됨**. "이 테스트를 통과하는 코드를 네가 써봐."
3. **박철원님이 구현** — 이 시간엔 기본적으로 개입하지 않기. 질문 오면 §3 의 힌트 사다리로 답변.
4. **실행** — 박철원님이 직접 `cmake --build && ctest` 를 돌리고 결과를 공유.
5. **리뷰** — 박철원님의 코드를 레퍼런스와 `git diff` 비교. 표면적 차이는 무시, 실질적 차이만 언급.
6. **커밋** — 박철원님이 원하면 커밋. 메시지는 박철원님이 먼저 써보도록 권하고, 괜찮으면 그대로 가기.

### 6.6 세션 끝낼 때
이 파일의 §8 Session Log 에 한 줄 기록 추가. 그리고 "다음 세션에 어디서부터 재개할지" 명시.

## 7. 레퍼런스 솔루션 사용 지침

- **레퍼런스 위치:** `main` 브랜치. 커밋 히스토리가 마일스톤 순서대로 쌓여 있음.
- **특정 Task 의 레퍼런스 코드를 보려면:** 그 Task 를 다룬 커밋의 해시로 `git show <sha> -- <path>`.
- **박철원님 코드와 레퍼런스 비교:** `git diff guided-learning main -- server/net/ws_frame.cpp` 같이 파일 단위로.
- **보여줘도 되는 것:** 테스트 코드, 헤더 파일의 선언(시그니처), RFC 섹션 번호.
- **보여주면 안 되는 것 (요청 없이는):** 구현 전체, 특히 `.cpp` 파일들.
