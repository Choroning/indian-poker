## 📝 About This Project

Indian Poker is a simple card game where each player is dealt one card and holds it up to their forehead — you can see everyone else's card, but not your own. Players then bet based on what they see (and what they can guess about their own card), and the highest card among those who stay in wins the pot.

This repository implements that game as a browser-based multiplayer mini-game, with one important twist: **the server is written from scratch in C++ on top of raw TCP sockets, and the WebSocket protocol is implemented by hand** (rather than using a library). The goal is not just to build a working game, but to reinforce and deepen understanding of how real-time client-server communication works at the protocol level.

The architecture separates the reusable room/session/network infrastructure from the game-specific logic, so additional mini-games can be plugged in as future modules without rewriting the networking layer.

| **Operating Systems** (`DCCS309-01`) | Spring 2026 (current) | I/O multiplexing with `select(2)`, single-threaded event-driven concurrency, file descriptor management, race-condition avoidance without locks |

The prior Computer Networks term project (a simple HTTP server in Python) and the OOP term project (a multiplayer chat application in Java with `ServerSocket`) both serve as direct stepping stones. This project extends those experiences in two directions at once:

1. **Deeper protocol work** — HTTP was a known, text-line protocol. WebSocket (RFC 6455) introduces binary framing, masking, opcodes, fragmentation, and control frames, which must be parsed and generated byte by byte.
2. **Different concurrency model** — the Java chat server used thread-per-connection; this project uses a single-threaded `select()` event loop to match the I/O multiplexing concepts currently being covered in Operating Systems.

<br><a name="game-rules"></a>
## 🎴 Game Rules

- **Players per room:** 2 to 4 (decided at room creation).
- **Deck:** numbered cards from 1 to 10, reshuffled each hand.
- **Hidden information:** each player sees every other player's card, but not their own.
- **Hand flow:**
  1. Every remaining player pays the ante into the pot.
  2. Each player is dealt one card.
  3. A single betting round proceeds clockwise. On their turn, a player may **Check** (match the current bet), **Raise** (increase the bet), or **Fold** (drop out of the hand).
  4. Betting ends when every still-active player has matched the highest bet, or when only one player is left.
  5. Remaining players reveal their cards. Highest card takes the pot.
- **Elimination:** a player with zero chips is out. The game ends when only one player remains.

## 🛠 Technology Stack

**Server (written from scratch):**
- Language: **C++** (C++17 or later)
- Networking: POSIX BSD sockets — `socket`, `bind`, `listen`, `accept`, `recv`, `send`
- Concurrency: single-threaded event loop using **`select(2)`** for I/O multiplexing
- WebSocket: **RFC 6455 implemented by hand** — HTTP Upgrade handshake, frame parsing/generation, masking, fragmentation, ping/pong, close frames
- External dependencies: **OpenSSL** (SHA-1 + base64, used only for the WebSocket handshake), plus a JSON library for message serialization

**Client:**
- Static HTML/CSS + **vanilla JavaScript** — no React/Vue/Svelte, no build step
- Browser `WebSocket` API for transport
- `sessionStorage` used only to preserve the current room code across accidental page refreshes

**Deployment:**
- **Frontend (static):** Vercel — serves the landing page (room create / join screen) and the game UI
- **Backend (game server):** runs on a local machine and is exposed to the public internet via **Cloudflare Tunnel** (`cloudflared`), with TLS terminated at Cloudflare's edge so the C++ server only has to speak plain WebSocket
- The browser loads the page from Vercel and then opens a `wss://` connection to the Cloudflare-tunneled backend

## 🏛 Architecture Overview

The server is organized into three strictly layered modules, with each layer depending only on the layers below it:

```plaintext
+------------------------------------------------------------+
|  Layer 3: Game Logic                                       |
|    - IGame interface (start, handle_action, snapshot_for)  |
|    - IndianPoker : IGame                                   |
+------------------------------------------------------------+
|  Layer 2: Session / Room Infrastructure                    |
|    - Player (nickname, chips, connection status)           |
|    - Room (code, player list, game instance)               |
|    - RoomRegistry (create/lookup/cleanup)                  |
|    - Router (who should receive which message)             |
+------------------------------------------------------------+
|  Layer 1: Network / Protocol                               |
|    - TCPListener, Connection                               |
|    - WebSocketHandshake (HTTP Upgrade)                     |
|    - WebSocketFrame (decode, encode, masking, fragments)   |
|    - EventLoop (select fd_set management)                  |
+------------------------------------------------------------+
```

Key design principles:

- **Layer 1 knows nothing about the game.** It only delivers fully-assembled text messages up to Layer 2.
- **Layer 2 knows nothing about game rules.** It holds an `IGame*` and routes actions to it, but never inspects the game state.
- **Layer 3 knows nothing about the network.** The game logic is a pure state machine: `handle_action(state, player, action) → new_state + outgoing messages`. This makes the game logic fully unit-testable without any sockets.

See [`PROJECT.md`](PROJECT.md) for the full design document, including the application protocol, state machines, error handling, and testing strategy.
